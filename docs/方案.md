# WARDOGS 自动建造工具方案 v2（基于 1–4.png 实测）

> 目录整理后，参考截图位于 `assets/reference/1–4.png`，WARDOGS 回归截图位于 `assets/validate/` 和 `assets/validate/white/`；文中提到的 1.png/validate 均指这些目录下的文件。

## 0. 结论

方案可行，核心路线是“颜色检测 + 相对鼠标闭环 + 起锤期间瞄准 + 510 ms 左键”，不需要 YOLO 或训练数据。但原 v1 文档里的参数不能直接使用：

- `4.png` 的颜色检测本身是干净的（2187 px，唯一连通域），但宽高比 **2.15** 被 `0.8–2.0` 过滤掉，最终候选数为 0，状态机会永远停在 SEARCH；
- `3.png` 的宽高比 **1.90**，距离 2.0 上限只剩 0.10，光照/角度稍微变化就会重演 4.png 的问题；
- 原 HSV 下限 `S≥120` 距离 3.png 黄色路沿的 `S≈110–116` 只有很小余量，饱和度提高约 10% 就会出现能通过尺寸/填充率过滤的路沿误检；
- 单张黄叉模板无法覆盖透视变化：1.png 与 3.png 归一化形状 IoU 只有 **0.43**，与 4.png 只有 **0.35**，不能作为硬门槛；
- “白叉中心距屏幕中心 <40 px”与“不需要精确瞄准叉中心”矛盾：准星只碰到一条臂时整叉会变白，但白叉中心可能离屏幕中心 50–120 px（validate/white 实测 59–64 px）；
- 盲目先发 30 counts 的增益探测可能把黄叉提前变白（黄色消失）或把它推出画面，应改成远距离小探测 + 第一段修正位移的反馈估计。
- validate/ 的 6 张 WARDOGS 不同建筑/角度截图：按旧参数 **0/6 漏检**；原因不是形状，而是黄叉更暗/更橙（H≈24–26、V 可低至 170、R−G 比例更大），被 `H≥26 / V≥180 / |R−G|≤0.12G` 挡掉。放宽后 **6/6 检出**，每张唯一候选，包围盒中心见 1.2 表。

v2 已修正上述问题，并加入用户要求的完整流程：

1. 黄叉进入射程或白叉锁定后，左键按下 **510 ms**；前 450 ms 继续瞄准，最后 60 ms 停手等待落锤；
2. 松手后等待黄叉移动到附近，重新瞄准；
3. 每完成 N 次（默认 4 次）瞄准建造，执行一次 **不瞄准黄叉** 的左键点击；
4. 鼠标移动使用贝塞尔曲线、随机弯曲、抖动、反应延迟和长短停顿，不画机械直线。

## 1. 实测数据

### 1.1 原过滤器复现

原方案参数：HSV `[20,120,160]–[38,255,255]`，RGB 附加条件，3×3 开/闭运算，面积 800–20000，宽 40–400，高 30–300，填充率 0.15–0.60，宽高比 0.8–2.0。

| 图片 | 黄色像素/连通域 | 包围盒 | 宽高比 | 原过滤器 |
|---|---:|---|---:|---|
| 1.png | 3813 px / 1 | (999,738,141,100) | 1.41 | 通过 |
| 2.png | 0 px | — | — | 白叉 4030 px，中心偏差约 1 px |
| 3.png | 2650 px / 1 | (975,756,118,62) | 1.90 | 通过，临界 |
| 4.png | 2187 px / 1 | (1463,770,103,48) | **2.15** | **拒绝**（>2.0） |

结论：3.png 能识别；4.png **最终候选数为 0**；1.png 正常；2.png 白叉正常。4.png 的失败点只在形态过滤，不在颜色。

### 1.2 修正后的检测

1–4.png 的黄叉：`H≈29, S≈160–175, V=255`，RGB 约 `(255,250,82)`。validate/ 中 WARDOGS 不同建筑/角度的黄叉：`H≈24–26, S≈179–255, V≈170–244`，阴影处可低到 `V≈170`，RGB 可从亮黄变到深芥末色。3.png 右侧黄色路沿：`H≈16–21, S≈103–116, V≈184–229`，RGB 约 `(229,199,129)`。

修正后的参数：

- HSV：`H 22–36`、`S≥130`、`V≥110`（覆盖 WARDOGS 阴影/暗光；H≥22 排除路沿）；
- 色度：`B ≤ 0.55·G` 且 `|R−G| ≤ 0.35·G`；
- 面积 600–12000，宽 40–400，高 30–300（排除建造后偶发的 35×42 px 黄色 UI/小物体）；
- 填充率 0.15–0.65，宽高比 **0.45–3.0**（validate v6 已到 0.60，给更斜/更窄的角度留余量）。

### 1.3 白叉锁定

2.png 白叉：原阈值下 bbox `(1205,675,149,93)`、约 3892 px；严格阈值下约 `(1214,678,138,88)`、3668 px（阈值差几像素属正常）。中心约 `(1277,718)`，与屏幕中心偏差约 1 px。中心 9×9 邻域 `V=255, S≈1`；其余三张图中心 `V=16/132/87` 或 `S=15/51`。

v2 不使用“白叉 bbox 中心距 <40 px”，而是：

1. 优先检查屏幕中心像素是否属于白色连通域；
2. 如果游戏准星覆盖了白叉中心（中心像素是准星而不是白色），则允许“白色连通域的 bbox 包含屏幕中心”作为回退；
3. 该连通域面积/宽高/填充率在范围内；白色掩码先试 `V≥185/S≤50`，失败再用 `V≥170/S≤55` 的放宽掩码；
4. 白叉候选中心必须在准星 **120 px** 内；validate/white 的 X 中心离准星约 59–64 px，游戏仍然显示可建造；
5. 中心白叉优先：即使黄色掩码仍看到一个残影/描边，只要准星中心是有效白色连通域就锁定；偏离中心的白叉候选才要求当前没有黄色候选（防止白色建筑背景误锁）；
6. 默认 1 帧确认（白叉检测已经用连通域形状/面积过滤；想更保守可配置 2 帧）。

这样准星落在 X 的任何一条臂上都算锁定，符合“不需要精确瞄准叉中心”的实际手感。

如果检测到白叉候选但中心距准星超过 120 px，AIM 会最多 2 次朝白叉候选中心移动（`aim.white_recover_radius_px=450`、`white_recover_max_attempts=2`），而不是立刻回到 SEARCH 等黄叉。若一次修正让目标越过准星，增益更新会从 EMA 切换为更大幅度的实测增益校正，减少连续过冲导致的丢失。

## 2. 完整建造流程

```text
F8 启动
  ↓
截取游戏客户区
  ↓
检测黄叉（唯一/离屏幕中心最近）
  ↓
拟人化鼠标移动：弯曲路径 + 抖动 + 延迟
  ↓
重新截屏确认黄叉变白（默认 1 帧；保守可 2 帧）
  ↓
左键按下 → 前 450 ms 继续瞄准 → 最后 60 ms 停手 → 松开
  ↓
chain=true：立即按下下一锤，在下一锤抡锤期间等待/瞄准新黄叉
  ├─ 新黄叉位移 ≥ chain_min_move_px → 上一锤完成计数 +1 → 继续
  ├─ 位移不足 → 上一锤未完成 → 继续瞄准当前黄叉
  └─ 整个窗口无黄叉 → 失败计数 +1 → 回到 AIM/SEARCH；连续 3 次 → 暂停

chain=false：轮询最多 2 s 确认新黄叉 → 再进入下一锤
```

### 2.1 单次建造

- 黄叉在 `swing.max_start_error_px`（默认 420 px）内，或白叉已经锁定时，直接按下左键起锤；不强制先等白叉。
- 按下后前 `hold_ms - strike_guard_ms`（约 450 ms）边抡锤边闭环瞄准黄叉；最后约 60 ms 停止移动，等待落锤。
- `swing.chain` 默认关闭（实测旧模式 10 次/6.1 s，链式首轮 14 次挥锤才完成 10 次）；用 `--chain` 启用链式：松开左键后**不等待新黄叉确认**，立即按下下一锤；在下一锤的 510 ms 抡锤期间轮询新黄叉并瞄准。游戏在旧黄叉被敲掉的同一时刻生成新黄叉，因此下一锤有完整的约 450 ms 瞄准窗口。
- 链式模式下上一锤是否完成，用“新黄叉相对预测旧位置的位移”判定；相邻黄叉不会重合，`swing.chain_min_move_px` 默认 40 px。新叉出现即表示旧叉被敲掉、建造完成；即使 `aim_ok=False`，只要新叉出现也计为完成。
- `swing.chain_probe_ms` 默认 450 ms，即不在落锤前松开；即使没瞄准也完整落锤，拿 1/5 进度。设为 200 ms 可在看不到新叉时提前松开，但提前松开没有落锤、0 进度。
- 最新实测：链式 23 次按下左键完成 20 次建造，用时 12.66 s（633 ms/件）；3 次提前松开没有落锤，进度为 0。对比旧模式 612 ms/件，链式约慢 3.4%。旧模式仍作为默认；链式适合追求动作连贯。
- 30 锤实测：旧模式 30 锤/29 次已验证建造/19.55 s（652 ms/锤）；链式 30 锤/23 次已验证建造/15.97 s（532 ms/锤）。链式 3 次未看到新叉的左键保持 464–491 ms，已越过落锤点，按 1/5 进度计；把所有未建成落锤按 1/5 折算后，两者实际效率基本持平，链式约快 0–3%。旧模式仍为默认。
- 50 锤复测（更大样本）：旧模式 50 锤/49 次验证建造/34.01 s（680 ms/锤，约 1.44 件/s）；链式 50 锤/32 次验证建造/27.34 s（547 ms/锤），9 次未看到新叉按 1/5 折算后约 1.24 件/s，即使其余未建成落锤也按 1/5 折算仍约 1.30 件/s。链式比旧模式慢约 10–14%，旧模式明确更优并保持默认。
- 未瞄准落锤仍会获得 1/5 建造进度。因此链式模式下即使锤子遮挡导致某一锤来不及瞄准，也只损失部分进度；下一锤新黄叉已可见，可继续补进度。
- 连续失败或整个抡锤窗口都看不到黄叉时，退出链式，回到 AIM/SEARCH 重新捕获目标；连续 3 次找不到目标仍会暂停。
- 锤子遮挡黄叉时使用最后一次有效黄叉/白叉中心继续修正，不会回 SEARCH；超过瞄准窗口仍未对准则本次落锤可能失败，下一轮继续。
- 链式瞄准在剩余时间不足约 220 ms 时改用低延迟快速微调（5–10 段、1–3 ms/段），补最后 20–50 px；正常瞄准仍使用拟人化曲线。
- 左键保持 `510 ms`（配置 `click.hold_ms`），松开后等待 5–12 ms 再开始轮询；轮询间隔 10 ms。
- 落锤后的前 350 ms 只做中心 ROI 轮询，避免新黄叉尚未出现时触发一次约 250 ms 的全屏回退；350 ms 后仍没有目标才回退全屏。
- 轮询到新黄叉后只保留 0–8 ms 微停顿，直接进入下一轮 AIM/CLICK；不再插入 20–60 ms 建造间隔，也不默认触发每 8 次一次的 200–350 ms 长停顿（`human.long_break_every: 0`）。
- 移动后的那一帧如果已经是白叉锁定，直接进入 CLICK 并复用该帧；新黄叉的轮询帧同时作为 AIM 和 CLICK 的首帧，起锤前不再重复截屏/检测，节省约 40–70 ms。
- 逐帧观察显示，新黄叉在旧黄叉被敲掉的同一时刻出现；日志中的 74–323 ms 主要是我们的检测/遮挡延迟，不是生成延迟。非链式模式最多等 2 s，`click.poll_ms=10` 连续发起 ROI 轮询（单次抓屏+识别约 50 ms）。
- 成功判据：点击后检测到新的黄色 X，并且相对**挥锤后旧 X 的预测位置**移动至少 `click.min_move_px`（默认 12 px）。预测位置 = 起锤前 X 的位置 + 挥锤期间净鼠标 counts × 增益；如果挥锤没能锁定/对准，判定距离会提高到 60 px。这样即使点击没生效、同一个 X 还留在原地，也不会被误判成“新黄叉”。
- 建造成功后，游戏可能让旧的白叉在准星处残留一小段时间，同时新黄叉已经出现在旁边。此时中心的白叉不是新的可建造目标；`swing.stale_lock_min_px` / `stale_lock_hint_px` / `stale_lock_max_age_s` 会把它识别为“陈旧锁定”，继续朝刚确认的新黄叉挥锤瞄准，而不是原地起锤。
- 陈旧锁定只在“上次轮询刚确认过的新黄叉位置”附近生效，避免把场景中的其他黄色物体当成目标。
- 如果点击后一直是白叉，说明可能“物资不足”或预览无效；连续 3 次暂停，避免无限空点。

### 2.2 非瞄准点击

配置 `miss.every_n_builds=4`：

- 每完成 4 次瞄准建造，下一次循环先执行一次“非瞄准点击”；
- 要求黄叉是黄色且距离屏幕中心 ≥120 px，确保准星没有落在黄叉上；
- 如果黄叉太近，先做一次拟人化“看向别处”的移动，再点击；
- 该点击保持 510 ms；它可能实际建出东西，也可能什么都不发生，取决于准星处的预览；
- 单独计数为 `non_aim_clicks`，不混入 `aimed_builds`。

## 4. 检测模块细节

1. 截取窗口客户区（`GetClientRect` + `ClientToScreen`），屏幕中心即客户区中心；无边框全屏时等于屏幕中心。
2. 启动/丢失目标时全屏检测；瞄准和点击后轮询只检测屏幕中心 `1000×1000` ROI（`detector.roi_half=500`），ROI 没有黄叉/白叉时自动回退全屏。
3. `detector.fast_mode=true` 时先 2 倍降采样找黄色候选，再回全分辨率局部确认；白叉锁定只处理中心 320×320 小图。找不到目标/需要完整白叉候选时回退原 detector。实测全屏检测约 10 ms（原约 80–130 ms），ROI 约 3 ms（原约 27 ms）。
   - 30 锤实机：旧模式 ROI 检测中位数 36.1→10.7 ms、全屏回退 129.6→39.9 ms、每锤 680→634 ms；链式 35.4→9.1 ms、约 156→41 ms、547→533 ms。
4. BGR → HSV；用窄 HSV 范围 + `B/G`、`|R−G|/G` 色度条件生成黄色掩码。
5. 3×3 开运算去噪、闭运算连接笔触断裂。
6. 连通域过滤：面积、宽高、填充率、宽高比。
7. 多个候选时取离屏幕中心最近的一个。
8. 默认首帧即可进入 AIM（`stable_frames: 1`）；黄色候选已用面积/宽高/色度过滤，想更保守可配置 2 帧。
9. 黄叉存在且准星中心不亮时跳过白叉计算；中心明显发白时仍然计算白叉，避免黄色残影导致漏掉已对准的白叉。
10. 黄叉首帧直接进入 AIM 并复用该检测；点击后轮询到的新黄叉直接作为下一轮 AIM 的首帧，避免重复截屏/检测。
11. 不把单张模板作为硬门槛；如需模板，只能做软评分。

## 5. 鼠标控制

### 5.1 相对输入

- 使用 `SendInput` 的 `MOUSEEVENTF_MOVE` 发送相对鼠标计数；不用 `SetCursorPos`/`pyautogui.moveTo`。
- 启动时设置 DPI 感知，避免 Windows 缩放下窗口坐标错位。
- `timeBeginPeriod(1)` 提高 sleep 精度；退出时恢复。

### 5.2 增益

`g = Δ屏幕像素 / Δ鼠标 counts`，x/y 分别维护：

- 默认 `gx=gy=-0.55`（鼠标右移，世界目标在屏幕上左移，所以为负）；
- 首次黄叉距离 >150 px 时，沿误差较大的轴发送 **12 counts** 小探测；测量后设置该轴增益；另一轴同理；
- 探测只在远处进行，避免“目标已经变白/在边缘”时探测失败；
- 每次实际修正后用观测位移更新：`g ← 0.65g + 0.35·(Δc/Δm)`；
- 只接受 `0.05 ≤ |g| ≤ 5`，避免异常值；x/y 独立，兼容横纵灵敏度不同或 Y 轴反转。

### 5.3 拟人化轨迹

每次修正的净 counts 固定，但路径不是直线：

1. 先随机等待 10–35 ms（反应延迟）；
2. 用三次贝塞尔曲线连接起点和终点，控制点沿垂直于直线的方向随机偏移 8%–22% 路径长度，形成弧线/绕远；
3. 用余弦 ease-in-out 分成 14–20 小段；
4. 每段加高斯抖动（σ≈2.8 counts，8% 概率使用 σ≈4.5 的较大抖动），并有 3% 概率插入 5–12 ms 的额外停顿；
5. 终点附近额外做 6%–10% 的小过冲（最多 30 counts），停 4–10 ms 后再反向修正，净终点仍然准确；
6. 最后把抖动造成的残差分成小段补齐，保证终点准确；
7. 移动后等待 8–20 ms，再由主循环等待 25–50 ms 让相机稳定，然后重新检测。

单次修正同时限制 360 counts 和 520 屏幕像素，最小 6 counts。360 counts 把常见误差压缩到 1–2 次修正。alpha 远处 0.88、近处 0.76；14–20 段、段间 3–5 ms，使甩枪更平滑，但移动前/后等待和建造间隔压得更短，整体效率更高。

### 5.4 点击

- 起锤条件：白叉锁定，或黄叉误差在 420 px 内；
- 左键 down → 前约 450 ms 持续瞄准 → 最后约 60 ms 停手 → 精确等待到 510 ms → up；
- 按下期间每 10 ms 检查 F9；如果急停，`finally` 保证松开左键；
- 点击后随机等待 8–20 ms 再轮询新黄叉（轮询间隔 10 ms）。

## 6. 状态机

```text
IDLE
 └─ F8 → SEARCH

SEARCH
 ├─ 黄叉首帧稳定（默认 stable_frames=1）→ AIM
 ├─ 白叉锁定（默认 1 帧，可配置 2）→ CLICK
 ├─ 黄叉消失 → 持续检测（每 5 s 日志），不会自动暂停；F9 手动停止
 └─ 从未见过 → 等待，不移动/不点击

AIM
 ├─ 白叉锁定（默认 1 帧）→ CLICK
 ├─ 黄叉：计算误差 → 拟人化移动 → 稳定 → 重新检测
 ├─ 迭代 >10 次 → PAUSED
 └─ 目标丢失 → SEARCH 持续检测

CLICK / 起锤
 ├─ 左键 down → 450 ms 内瞄准黄叉 → 最后 60 ms 停手 → 510 ms up
 ├─ 2 s 内出现移动 ≥12 px 的新黄叉 → 成功
 ├─ 仍是白叉 → 失败 +1 → 重试；3 次 → PAUSED
 └─ 成功后每 N 次 → MISS

MISS（非瞄准点击）
 ├─ 黄叉距离 ≥120 px → 510 ms 点击 → SEARCH
 ├─ 太近 → 拟人化看别处 → 再判断
 └─ 无法安全执行 → 跳过并记录

PAUSED
 ├─ F8 → 恢复
 └─ F9 → 退出并松开左键
```

起锤期间锤子会遮挡画面；瞄准循环使用最后一次有效 X 中心，遮挡时不会丢失状态。

F8 同时是开始/暂停/恢复键；F9 在任何移动或 510 ms 按住期间都能中断。
F8 使用 `GetAsyncKeyState` 的按下锁存位，快速点按即使在挥锤期间松开也会被记录，暂停在当前步骤结束后生效；频繁连续点按可能合并为一次。

## 8. 异常与安全

- **前台窗口检查**：每轮输入前确认绑定窗口在前台；Alt-Tab 后只检测不输入，回到前台自动继续。
- **窗口关闭/最小化**：窗口句柄无效或客户区不可用时暂停/退出，不盲目发点击。
- **左键无反应**：当前实现已经使用 `INPUT type=INPUT_MOUSE(0)` + `MOUSEEVENTF_LEFTDOWN/UP` 的 `SendInput`，和手写的 C 结构等价；先用 `--test-click` 在记事本验证注入是否成功，再检查游戏前台、管理员权限、独占全屏和“系统光标是否跑出客户区”。脚本默认 `click.ensure_cursor_in_window: true`，点击前会把跑出客户区的光标移回中心。若记事本有效而游戏无效，通常是游戏/反作弊不接受软件注入输入，应使用官方支持的手柄/宏/手动操作，不要尝试绕过反作弊。
- **管理员权限**：游戏以管理员运行时，脚本也需管理员权限，否则 `SendInput` 可能被拦截。
- **独占全屏**：`mss` 可能截到黑屏；优先无边框窗口；可选 `dxcam` 后端。
- **HDR**：颜色可能整体变化；`config.yaml` 可调阈值，白叉有自适应亮度回退。
- **物资不足**：不 OCR 中文提示，而是用“点击后仍是白叉”判定；连续 3 次暂停。
- **急停**：F9 中断移动/按住，退出时释放左键；不会留下按住状态。
- **最大次数**：`--max-builds N` 或 `click.max_builds` 限制瞄准建造数；达到后脚本正常退出（日志会明确提示），`0` 为不限。连续建造请去掉该参数；启动日志会打印当前运行模式。
- **在线游戏风险**：自动输入可能违反游戏服务条款；建议先在离线/私人环境验证，不要直接用于正式账号。脚本不修改游戏文件、不读取游戏内存、不绕过反作弊。

### 9.3 Debug 逐步计时

```powershell
python auto_build.py --debug
```

`--debug` 适合连续建造观察，持续输出：

- `DET`：抓屏、检测耗时，黄/白候选数、锁定、V/S、bbox、误差；
- `AIM` / `CALIB`：规划、移动、稳定、移动后检测耗时，counts 和增益；
- `WHITE`：白叉确认帧数、V/S、进入 CLICK；
- `SWING`：起锤后的瞄准次数、目标、剩余时间和 60 ms 停手窗口；
- `CLICK`：起锤前等待、510 ms 按住（含抡锤瞄准）、松开后等待；
- `VERIFY`：点击后轮询次数/耗时和是否找到新黄叉；
- `BUILD`：每件建造总耗时与累计建造数；
- `WAIT` / `MISS`：建造间隔、长停顿、非瞄准点击。

普通运行不打印 trace；`--debug` 同时把日志级别设为 DEBUG。日志时间精确到毫秒。

### 9.4 已知限制

- 极暗表面上的白叉可能低于 `V=235`，已加入 `relaxed_v/dv_min` 回退，但仍建议实机确认；
